## 1. Executive summary — plain language first

**The single most important thing in this report:** this repository currently contains **three separate mechanisms that run hidden code on the machine of anyone who opens, clones, or runs parts of it**. They look planted rather than accidental, and they should be treated as a suspected compromise until proven otherwise:

1. Opening the repo in **VS Code** can silently run an obfuscated JavaScript file disguised as a font (`.vscode` auto-run task, console hidden).
2. Running the documented **OpenCode setup** (`npm start` in `STM_HRTS/opencode`) runs a second obfuscated payload appended to a benign stub file.
3. Running the **STM_HRTS Python console** imports a module that fetches JavaScript **from an Ethereum transaction** controlled by one hardcoded wallet address and executes it with Node — an on-chain dead drop. The payload is not in the repo, is not pinned or signed, and can be changed by whoever holds that wallet at any time.

Machines that have opened this repo in VS Code, run that `npm start`, or run the STM_HRTS console should be checked before they are trusted. Section 4 gives the full evidence (findings A5-1, A5-2, A1-1).

**The product itself** (a P2P metaverse: Godot world + C# viewers + Python services) has a session-security model that is not yet true against a hostile peer:

- **Identity is a claim, not a proof.** A player's UUID is a self-generated string with no key pair or signature — and it is broadcast to every peer, so anyone can copy it and return as that player, reclaim their island, and impersonate them in chat. (V2)
- **LAN sessions have no credential at all.** The invitation token only guards the tunnel path. On a local network, anyone can join — and anyone can broadcast a fake "host here" beacon and become the host for other players. (H7)
- **The chat relay authenticates nobody** and listens on all interfaces; identity in chat is whatever name/UID a client asserts. (G1)
- **Peers' home IP addresses and tunnel URLs are broadcast to the whole session** and written to disk alongside the session invitation itself. (G4)
- **The update chain can be turned into remote code execution for the whole fleet:** release binaries are unsigned, and the SHA-256 that "verifies" an update comes from the same GitHub API response as the download URL — one compromised release account controls both the payload and its expected hash. The Windows apply step additionally never re-checks the file it installs, and the Linux updater accepts a package with no digest at all. (G3, H3, G2)
- **Supporting tools are downloaded and executed unverified** — cloudflared from a mutable "latest" URL (M19) and, in dormant code, the IPFS Kubo daemon the same way.
- **The Python ledger destroys itself quietly:** any read error silently replaces the whole blockchain ledger with a fresh genesis block (H1), fake "local" IPFS CIDs are mined into it as if real (M13), and the publish flow deletes local records after an upload that never happened (V5).

**Where the project's own plan stands:** the repo's Implementation Plan Stage 1 (P2P session security) has 7 work items. Five are addressed by open pull requests from the collaboration (#57 G4, #58 G1, #59 H2, #60 H6+M21, #61 V2) and one further hole found by this audit (unauthenticated `/peer` registration) is addressed by #62. **Two Stage 1 items remain open even if all those PRs merge: H7 (LAN credential) and M22 (host-migration trust)** — and several PR-addressed items have residuals noted in their findings. Of the plan's 15 High findings (H1–H15), this audit confirmed all 15 in the code at the audited commit (H5 is graded Medium here; see its finding).

**Totals (after de-duplication across crews): 74 findings — 6 Critical, 23 High, 30 Medium, 10 Low, 5 Info.** Of these, 33 verify or extend findings from the project's own Implementation Plan and 41 are new. Details, evidence, and fixes per finding are in Section 4; the companion document `SECURITY_ROADMAP_2026-11-05.md` turns them into PR-sized fix slices.

### 4.1 Critical

#### A1-1 — Import-time remote code execution fetched from an Ethereum transaction (on-chain dead drop) — Critical · NEW · OPEN

> ⛔ **ABSOLUTE CRITICAL SHOWSTOPPER — HARMFUL CODE.** This mechanism is a malware-style loader: it secretly fetches unsigned JavaScript from an Ethereum transaction and executes it. The 2026-11-05 provenance trace proved it delivers the **same byte-identical second-stage loader** as A5-1 and A5-2, which downloads further code from **live command infrastructure** — this is a backdoor, **not** a legitimate Web3 update method. **Remove before anything else (roadmap R-01).** Any machine that ran the STM_HRTS console must be treated as potentially compromised. (Honest limit: the final downloaded stages were never fetched or run; which human planted this is not proven.)
- **Location:** `$SRC/STM_HRTS/utils/transport.py:1-58`; imported at `$SRC/STM_HRTS/__main__.py:10`
- **Evidence:** At module top level (no function, no `__main__` guard, whole body inside a silent `try/except Exception: pass`): `_addr = "0x3b1574417524c11a7403c4b232CAcBb320CceBC6"`; it queries `https://api.ethplorer.io/getAddressTransactions/{_addr}?apiKey=freekey…`, takes the first transaction whose `from` equals that address, fetches it via `eth_getTransactionByHash` from `https://ethereum.publicnode.com`, then `_source = bytes.fromhex(_rpc["result"]["input"][2:]).decode()`, writes `_source` to a temp `.js` file, runs it with `node`, and unlinks the file.
- **Impact:** Whoever controls that one Ethereum address controls arbitrary JavaScript executed, as the user, on every machine that imports this module — `__main__.py:10` does `import utils.transport`, so running the STM_HRTS console triggers it. The payload is not in the repo, is not pinned, signed or hashed, can be changed at any time by a new transaction from the address, and all failures are swallowed so there is no visible trace except the outbound requests. Functionally indistinguishable from a supply-chain backdoor / malware loader, regardless of author intent.
- **Recommended fix:** Delete `transport.py` and its import immediately; treat any machine that has run `python -m STM_HRTS` (or otherwise imported it) as potentially compromised and investigate what payload the referenced transaction(s) carried. No code in the project should ever fetch-and-execute remote code at import time.
- **Confidence:** Verified (code read in full; reachability via the `__main__.py` import verified). The current on-chain payload was deliberately **not** fetched or executed.

#### A2-1 — No peer authentication: self-asserted UUIDs are identity in game and chat — Critical · Plan V2 CONFIRMED · ADDRESSED BY OPEN PR #61
- **Location:** `$SRC/MTBGT/WoldVirtualP2P3D/gdscrip/Identidad.gd:14-22,42-44`; `ChunkManager.gd:443-452` (`_claim_island`), `503-531` (claim resolution), `580-594`, `882-903` (`_spawn_island_for_player` broadcast), `685-692`; `Construccion.gd:254-262` (`_es_mi_isla`); `$SRC/VSC#/Chat/ChatRelayServer.cs:242-262` (`hello`); `ChatProtocol.cs:61-76` (`CleanUid`), `102-108` (`BuildFallbackUid`)
- **Evidence:** Identidad generates the UUID locally with no key pair: `uuid = Crypto.new().generate_random_bytes(16).hex_encode()`; validity is form only (32 hex chars). The host accepts any well-formed UUID at face value: `pending_uuids[sender] = uuid if Identidad.uuid_valido(uuid) else ""`. The host then **broadcasts the UUID to every peer** (`_spawn_island_for_player(id, index, nick, uuid)`; stored in `island_owners`, "vive en TODOS los peers"), and it is also recoverable from prims file names (`prims_<idx>_<uuid>.json`) on any machine that saved the island. With an **empty** UUID, claims fall back to raw index trust for not-yet-registered islands. Chat is identical: the relay takes `uid` from the client's `hello` after charset sanitising only; if empty it derives one deterministically from the display name (`SHA256("wvp3d-user:" + name)`), so two people with the same name collide by design. - **Location:** whole VSC# tree; `$SRC/VSC#/AppExtractor.cs:170-196`; `$SRC/VSC#/VisorLinux/Linux/RuntimeLinux.cs:184-205`
- **Evidence:** Repository-wide search found no BinaryFormatter, SoapFormatter, LosFormatter, NetDataContractSerializer, Newtonsoft TypeNameHandling, XmlSerializer/DataContractSerializer on untrusted data, or JsonConvert at all. #### A4-18 — MainWindow is a ~3,420-line god class holding all security-critical flows — Info · Plan M20 CONFIRMED as context
- **Location:** `$SRC/VSC#/MainWindow.xaml.cs` (3,420 lines)
- **Evidence/impact:** One WPF window class simultaneously implements credential validation and password-hash migration (~3062-3110), access-key verification and rotation (747-856), hardware-hash computation (3123-3160), the OTA download/apply trigger (424-490), both public-tunnel implementations incl. cloudflared download (3232-3420), P2P session/peer handling (~1300-1530), chat session management (~1428-1800) and Godot process launching (862-935). Security angle only: credential material, untrusted network input (invitation links, tunnel output, chat) and code-execution triggers (update apply, process launches) all share one untestable UI class with broad mutable state, so a defect or a careless edit in any feature can silently affect the authentication and update paths, and the security logic (e.g. the A4-3 key check inside a click handler) cannot be unit-tested in isolation — the project instead relies on whole-app selftests. This structure is how several findings above (A4-3, A4-5, A4-16) ended up embedded in event handlers.
- **Fix:** Extract authentication/key verification, the updater client and tunnel management into the existing service classes (as was done for STM_actualizar), with the window calling them; add focused tests for the extracted security decisions. **Confidence:** Verified.

#### A5-16 — Godot project ships with an enabled editor plugin that deletes files, and with PCK encryption off — Info · NEW · Posture note
- **Location:** `$SRC/MTBGT/WoldVirtualP2P3D/project.godot` (application, editor_plugins, autoload sections); `$SRC/MTBGT/WoldVirtualP2P3D/addons/limpiar_cache/plugin.gd`; `$SRC/MTBGT/WoldVirtualP2P3D/export_presets.cfg:19-20`
- **Evidence/impact:** project.godot is a standard (non-.NET) Godot 4.7 project: config/features = ("4.7", "Forward Plus"), one autoload (OptimizadorAvatares), one enabled editor plugin (`res://addons/limpiar_cache`). That plugin is `@tool` EditorPlugin code — it executes whenever the project is opened in the editor — and on play-stop and on editor exit it recursively deletes unreferenced files in the `.godot/imported` folder and empties the shader_cache and editor subfolders. Deletions are confined to the regenerable `.godot` cache tree. export_presets.cfg (single Windows Desktop preset, x86_64, embed_pck=false) sets `encrypt_pck=false` and `encrypt_directory=false` with script_export_mode=2. Two posture notes rather than defects: (1) opening this project in Godot runs committed editor-plugin code that deletes files — scoped to cache, and mirrored by limpiar_cache_godot.ps1, but it means "just opening the project" is not a zero-effect action, which matters alongside A5-1; (2) exports ship the PCK unencrypted, so GDScript logic and assets in a release are trivially readable/modifiable by recipients.
- **Fix:** Document the plugin's behaviour at the project root (or disable it by default and opt in per-developer); if asset/script confidentiality matters, enable PCK encryption for release presets with the key held outside the repo. **Confidence:** Verified (project.godot read directly; no Godot import was run on the audit tree).

## 6. Coverage, verified negatives, and what is NOT PROVEN

### 6.1 Consolidated verified negatives (checked, no defect)
- **GDScript:** no `OS.execute`/`OS.shell_open` anywhere in the 65 `.gd` files; no path traversal via network strings (file names are built only from integer index + `uuid_valido`-gated UUID); host-forced avatar assignment is catalogue-gated; terrain/prims/voxel/appearance parsers sanitise per-entry values; the Sonda/EcoMundo probe stubs are a sound containment pattern (A3-14).
- **C#:** no unsafe deserialization anywhere (System.Text.Json with fixed DTOs only); no TLS certificate-validation disabling; the two runtime zip extractors (AppExtractor, RuntimeLinux) do explicit per-entry path containment; password storage is strong (PBKDF2-SHA256, 210k iterations, per-user salt, constant-time compare, legacy migration) (A4-14, A4-15).
- **Chat protocol mechanics:** frame sizes *are* capped (700 KB, including the 64-bit length path and fragmented accumulation), text/name/UID lengths are sanitised, per-client text/social rates exist, MaxClients is 16 — the gaps are *when* connections are counted (A2-11) and media rates (A2-12), not frame parsing.
- **Godot build RPCs:** `_solicitar_*` editing requests *do* validate island ownership server-side via `_validar_remitente` — the residual risk is that ownership itself rests on the self-asserted UUID (A2-1).
- **P2PNodo's own accept loop** continues on generic exceptions (`catch { }`), unlike WebNodo's (A2-3).
- **Secrets, current tree:** no private-key blocks, no GitHub-token patterns, no real provider API keys anywhere in the current tree; only the vault seed constant (A1-5), a masked key fingerprint in a doc (A5-14), placeholders and test fixtures.
- **Scripts sweep:** destructive deletes exist only in the three utils .ps1 files (A5-8, A5-9, limpiar_cache_godot.ps1); no pipe-download-to-shell pattern exists in any shell/batch/PowerShell script (the download-and-execute pattern is in C# and Python, A4-5/A1-1); no committed exe/dll/zip/pck binaries exist in the current tree (verified via `git ls-files` + file-type inventory).

### 6.2 NOT PROVEN — checks that could not be run under the read-only rule, stated honestly
- **Payload behaviour (A5-1, A5-2, A1-1) — UPDATED 2026-11-05 by the provenance trace:** the payloads were deobfuscated **statically** in a disposable no-network sandbox (never executed) and all three mechanisms proved to converge on **one byte-identical second-stage loader** that resolves server addresses from the newest transaction of the dead-drop wallet and downloads XOR-scrambled code from live command infrastructure (`95.135.181.151` as of 2026-11-05). The **final downloaded stages were never fetched and never run**, so their ultimate behaviour remains **unknown and NOT PROVEN**; what is proven is the harmful delivery mechanism itself. Full evidence: `PAYLOAD_PROVENANCE_TRACE_2026-11-05.md`. (At the time this audit was written, sandbox deobfuscation was roadmap item R-01b.)
- **Python dependency vulnerabilities:** pip-audit is not installed on the audit machine and installing it was out of scope → per-package CVE status is **NOT PROVEN**; pyproject.toml was assessed by version-range inspection only (A5-12).
- **.NET dependency vulnerabilities:** `dotnet list package --vulnerable` requires a restore that writes `obj/` into the tree — forbidden by the read-only rule → **NOT PROVEN**; versions were assessed by direct .csproj inspection (A5-10, A5-12). (dotnet 8.0.427 is present on the machine.)
- **Godot runtime behaviour:** Godot was **not** run/imported against the audit tree (an import writes `.godot/`); project posture was assessed by reading project.godot, export_presets.cfg and addon source (A5-16). No live two-machine session was run — all network findings are from code, not from a live hostile-peer test.
- **Git-history secrets, exhaustive:** the history check was bounded — `git log --all -S` pickaxe for the master-seed constant, OPENROUTER_API_KEY and the provider key prefix across all 213 commits, plus `git grep` for provider-key/GitHub-token/private-key patterns and the seed at five sampled revisions (HEAD c0aaa84, 78a1dd0, d510acd, 90688d5, 575fccb). Result: no real key/token/private-key material found; the master seed is present at every sampled revision. An exhaustive grep of every tree at every one of the 213 commits for every pattern was **not** done — uncovered history is NOT PROVEN. No dedicated secret scanner (gitleaks/trufflehog/semgrep) is installed on the machine; an automated entropy-based scan is likewise NOT PROVEN.
- **A1-19 and A4-16** are graded "needs verification" in their findings (mitigations appear to block the obvious exploit paths; the patterns are fragile rather than proven-exploitable).
- **Test-suite state:** the crews did not re-run the Python suite against the audit clone (running it writes caches and the suite is environment-coupled per plan M26–M28). The roadmap therefore uses the established clean-main baseline — **94 passed / 2 pre-existing failures / 2 skipped** (plus the documented stale-`.pytest_cache` spurious failure) — as the acceptance yardstick rather than a fresh count.
